## HTTPS and proxy security findings

- Django currently has `SECURE_PROXY_SSL_HEADER = None`; `USE_X_FORWARDED_HOST` is not enabled. Production Compose sets `ENABLE_HTTPS=True`, which activates Django SSL redirects and secure session/CSRF cookies, while HSTS remains zero unless configured otherwise. Because Django does not recognize Nginx's `X-Forwarded-Proto: https` yet, HTTPS requests can be redirected repeatedly. Keep local settings unchanged; this is a production activation blocker.
- Nginx assigns `X-Forwarded-Proto` from its own `$scheme` and replaces forwarded host/IP headers, so it does not retain client-supplied values along its proxy path. However, the Compose web service is also attached to the internal `data` network; PostgreSQL and Redis peers share that network and can reach Gunicorn directly. The absence of a published Gunicorn port does not prove Nginx is its only trusted caller. Do not configure Django to trust forwarded HTTPS until the topology prevents untrusted direct access and that boundary is verified.
- Before activation, confirm domain ownership and DNS; serve a separate HTTP-only bootstrap config; obtain the real certificate; validate and activate the TLS server; test TLS and proxy behavior; then restrict Gunicorn reachability to the intended proxy path. Only after that should approved Django production settings trust `HTTP_X_FORWARDED_PROTO=https` and enable `ENABLE_HTTPS`, redirects, and secure cookies. Verify allowed hosts and HTTPS CSRF origins against the confirmed hostnames, and confirm redirects/cookies through the real proxy.
- Enable HSTS only after HTTPS works reliably for every hostname covered by the policy and rollback implications are understood. Keep `SECURE_HSTS_INCLUDE_SUBDOMAINS` and `SECURE_HSTS_PRELOAD` off until their broader scope is explicitly reviewed; preload remains disabled in this preparation. No HSTS, HTTPS redirect, local proxy trust, or production Django setting was activated during this phase.
- Production HTTPS, certificate validity/renewal, redirect handling, host validation through the live proxy, and spoofed-header behavior were not runtime-tested because no domain, real certificate, or production network exists. The synthetic certificate was used only for isolated Nginx syntax validation.

## Architecture review

- Production topology is isolated in `deploy/compose.production.yaml`; local `compose.yaml` is development configuration and remains untouched.
- PostgreSQL and Redis are attached only to the Compose `data` network, which is marked internal. Neither publishes a host port. Only Nginx publishes 80/443; Gunicorn is exposed to the Compose proxy network only.
- Web also joins the proxy network, so it can reach Nginx peers and has a network path with egress through that bridge. The database network itself is internal. Review egress restrictions if the threat model requires web-only SMTP egress.
- Compose interpolation values such as `POSTGRES_PASSWORD`, `DATABASE_URL`, `REDIS_URL`, and `APP_IMAGE` must be supplied to the Compose CLI environment (for example, with its `--env-file` option). The service-level `env_file` injects variables into the web container; it does not supply Compose interpolation values. Treat rendered Compose output as secret-bearing and do not save, publish, or paste it into logs.
- The app image is required as an immutable digest. PostgreSQL, Redis, and Nginx use pinned version tags but not digests; pin reviewed digests before deployment and define an image update process.
- The app has a read-only root filesystem, a non-root image user, and persistent volumes for private uploads/public media. Verify volume ownership with a disposable rehearsal. Nginx mounts only public media read-only; private attachments are not mounted into Nginx.
- Redis is authenticated, memory-bounded, and non-persistent with `allkeys-lru`. It is appropriate only while cache and rate-limit state are disposable; verify eviction behavior before launch.
- The web service uses `POSTGRES_USER` in `DATABASE_URL`. The PostgreSQL official image creates that role as a superuser; use a separate least-privilege runtime role before deployment.
- Web also joins the internal data network, so PostgreSQL and Redis peers can reach Gunicorn. No host port is published, but Compose does not provide directional peer filtering.
- The HTTP redirect reflects `$host`, allowing an unknown host to influence its destination. The Nginx upstream uses static DNS resolution and may need reload after web-container replacement.
- Redis expands its password into the `redis-server --requirepass` process argument as well as receiving it through the environment.
- No resource limits, host firewall, backup jobs, monitoring, certificate issuance/renewal, or recovery rehearsal are implemented by this template.

## Outstanding security blockers

Do not expose the proposed production stack publicly until these are resolved, reviewed, and validated:

- [BLOCKED] **HTTPS/proxy trust:** Compose enables `ENABLE_HTTPS=True`, but Django leaves `SECURE_PROXY_SSL_HEADER=None`; TLS-terminated requests can loop on redirects. The web container also shares the internal data network with PostgreSQL and Redis peers, so a proxy header cannot safely be trusted until direct Gunicorn access is restricted and that boundary is proven.
- [BLOCKED] **Database privilege:** the application database URL uses the PostgreSQL initialization role, which is a superuser in a fresh official-image database. Provision a separate least-privilege runtime role and keep migration/backup privileges separate.
- [BLOCKED] **Host redirect:** the HTTP Nginx redirect reflects `$host`; unknown Host values can influence the redirect destination. Use a fixed, confirmed canonical host or an explicit rejecting default server.
- [BLOCKED] **Private attachment URL behavior:** storage generates a `/media/` URL for a synthetic private path. The separate volume prevents Nginx from directly reading the private volume, but the failed regression test leaves URL generation unresolved. Obtain approval for the storage implementation change, then pass the regression test before launch.
- [BLOCKED] **Secrets and cache access:** Redis password is exposed through container environment and process arguments, and Redis uses its default ACL user. Reduce secret exposure and review Redis access policy before handling production credentials. Never publish rendered Compose output.
- [BLOCKED] **TLS template and images:** the Nginx config contains placeholder domain/certificate paths and combines TLS with an already enabled redirect, so it is not an HTTP bootstrap config and cannot start without valid certificate files. The exact pinned Nginx image has not passed syntax testing; use reviewed immutable image digests and validate the final config/certificate before activation.
- [BLOCKED] **Operations and recovery:** host firewall/SSH policy, resource limits, effective persistent-volume permissions, encrypted off-server backup implementation, key recovery, retention/alerts, and a successful isolated database-plus-upload restore are not in place or verified. Treat their absence as launch blockers for any production data.

Several blockers require application or deployment-template changes. They are documented only; no active Django settings, production Compose/Nginx template, credentials, local services, or data were changed to address them in this report update.
